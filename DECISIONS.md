# Решения по импорту и хранению

**Формат источника.** Варианты: один общий файл или отдельные выгрузки договоров, работ и платежей. Используются предоставленные `contracts.csv`, `works.csv`, `payments.csv`; их формат описан в `backend/data/FORMAT.md`. Чтение и проверка выполняются модулем `imports`. Если формат источника изменится, потребуется изменить парсер и DTO; расчёт отчёта останется отдельным.

**Повторный импорт.** Варианты: пропускать записи, отклонять изменения или обновлять по ID. По решению пользователя обновляем по `contract_id`, `work_id`, `payment_id`. Уникальность закреплена первичными ключами PostgreSQL. Если ID меняются между выгрузками, одна сущность может попасть в базу под разными ID; понадобится устойчивый ключ источника.

**Удаление отсутствующих записей.** Варианты: считать комплект CSV полным снимком и удалять отсутствующее либо сохранять накопленные данные. Выбрано сохранение: неполная выгрузка не должна удалять прежние платежи. Если требуется замена полного снимка, в отчёте могут остаться уже неактуальные строки; это потребует отдельного правила удаления или версионирования.

**Ошибки и дубли в CSV.** Варианты: пропускать ошибочные строки, брать последнюю строку с данным ID или отклонять импорт целиком. Выбрано отклонение всего комплекта CSV, включая повторённые ID: порядок строк не должен определять суммы. Проверка предшествует одной транзакции; ошибка связей с существующими записями также отменяет импорт. Если бухгалтеру нужен частичный импорт, потребуется отдельный отчёт об отклонённых строках.

**Ссылки между файлами.** Варианты: разрешать ссылки на любые существующие строки базы или требовать связанные строки в том же комплекте CSV. Выбран самодостаточный комплект: договоры и работы, на которые ссылаются строки выгрузки, должны присутствовать в её файлах. Если выгрузки приходят отдельными дельтами, понадобится проверка ссылок с учётом содержимого базы; сейчас такая выгрузка будет отклонена.

**Деньги.** Варианты: округлять входные значения или принимать только точные суммы с точностью до копейки. Выбран второй вариант: отрицательные суммы и лишние знаки отклоняются, в PostgreSQL храним целые копейки `BIGINT`, расчёт использует `bigint`. Если источник содержит более двух десятичных знаков, импорт будет отклонён до исправления исходных CSV.

**Источник отчёта.** Варианты: читать файлы при построении отчёта или получать сохранённые данные из PostgreSQL. По уточнению пользователя выбран PostgreSQL через Prisma. Подключение к базе обязательно. Чтение CSV выполняется модулем `imports`, а `report` получает данные через свой репозиторий Prisma. Отчёт отражает последнюю успешную загрузку источника; для актуализации есть расписание и ручное обновление.

**История изменений.** Варианты: хранить версии каждой загрузки или обновлять текущие данные. Выбрано обновление текущих данных по ID согласно запросу. Отчёт на прошлую дату использует последние импортированные сведения и даты событий. Если нужно воспроизводить ровно тот отчёт, который видели до исправления данных, понадобится хранение версий.

**Prisma.** Варианты: оставить прямой SQL или использовать ORM. По запросу пользователя доступ к учётным данным переведён на Prisma 7: чтение через модели и `findMany`, запись через `upsert`, операции объединены в транзакции. Имена таблиц, целые копейки `BIGINT` и даты PostgreSQL сохранены. Если типы или связи потребуется поменять, это оформляется отдельной миграцией.

**Переход существующей базы.** Варианты: пересоздавать таблицы или принять схему прежней версии за начальную миграцию Prisma. Выбран baseline при наличии прежней записи `001-accounting`; учётные данные не удаляются. Ограничения базы сохранены в SQL-миграции. Если база менялась вне приложения, её структуру нужно сверить отдельно: наличие прежней записи само по себе не описывает внешние изменения.

**Валидация DTO.** Варианты: ручная проверка всех значений или декораторы `class-validator` с отдельными проверками связей и учётных правил. По запросу пользователя выбран второй вариант. Он применяется к HTTP query и строкам CSV; неизвестные query-параметры отклоняются. Если появятся новые поля API, их нужно явно добавить в DTO, иначе запрос получит HTTP 400.

**Swagger.** Варианты: отдельное описание API или OpenAPI, собираемый из контроллеров и DTO. Выбран Swagger с вложенными схемами ответа, примерами, ошибками и ручкой обновления CSV. Если изменится маршрут или DTO, документация должна обновляться вместе с кодом; тест проверяет основные схемы и ручку обновления CSV.


**Первоначальная загрузка CSV.** Варианты: импортировать при каждом старте или сохранять отметку успешной загрузки в базе. Выбран второй вариант по запросу пользователя: запись `csv` в `import_states` сохраняется в одной транзакции с данными. Перезапуск не перечитывает источник. При первой ошибке сервер не запускается и следующий запуск повторит попытку. Если первичное наполнение нужно выполнить заново, используйте ручное обновление.

**Расписание и ручное обновление.** Пользователь выбрал обновление каждый час. По умолчанию импорт выполняется в начале часа по Москве; cron и часовой пояс настраиваются окружением. `POST /api/imports/csv/refresh` и кнопка интерфейса запускают ту же загрузку CSV немедленно. Ошибка плановой загрузки записывается в лог, предыдущие данные сохраняются, следующая попытка идёт по расписанию. Если нужен другой период, меняется настройка cron.
