# AGENTS.md

## Назначение проекта и требования

Программа строит отчёт по договорам, работам и платежам подрядчиков на выбранную дату.

Основные источники требований:
- `README.md` — исходное ТЗ и запуск.
- `backend/data/FORMAT.md` — значение полей исходной выгрузки.
- `DECISIONS.md` — принятые решения, допущения и их влияние на отчёт.

По каждой работе нужно показать цену, выплаченную сумму и остаток.
По каждому договору нужно показать итоги.
Контрольная дата из ТЗ — `2026-11-10`.

Деньги необходимо считать точно, до копейки, без вычислений с плавающей точкой.

В комплект для сдачи входят:
1. Программа с воспроизводимой инструкцией запуска.
2. `DECISIONS.md`: что решали, варианты, выбор и причина, последствия неверного выбора.
3. Записка бухгалтеру на 5–10 строк простым языком.
4. Подлинный полный экспорт всех сессий Claude Code командой `/export`.
   Допускается удалить попавшие в экспорт ключи и пароли.
5. Описание незавершённых частей, если они есть.

Не создавай и не подменяй транскрипт вымышленной историей работы.

Исходное ТЗ не требует интерфейса, базы данных и Docker.
В текущем проекте они уже реализованы как расширение.
Приоритет работы — правильность расчёта, понятные допущения и возможность запустить решение.
Не расширяй инфраструктуру без конкретной задачи.

Задание, исходные данные и решение нельзя публиковать.
Для сдачи используется приватный репозиторий или архив.

## Текущий стек и структура

- Backend: Node.js `>=24.15.0`, TypeScript в строгом режиме, NestJS 11.
- База данных: PostgreSQL; доступ через Prisma 7 и `@prisma/adapter-pg`.
- Frontend: React, TypeScript, Vite.
- Проверки: встроенный `node:test` и `node:assert/strict`.
- Планировщик: `@nestjs/schedule` и `cron`.

Основные каталоги:
- `backend/src/common/` — модели учёта, входные DTO, валидация, деньги и даты.
- `backend/src/modules/report/` — получение данных и расчёт отчёта.
- `backend/src/modules/imports/` — чтение CSV, проверка, запись и расписание.
- `backend/src/database/` — Prisma и запуск миграций.
- `backend/prisma/` — схема и SQL-миграции.
- `backend/test/` — расчёты, импорт и интеграционные проверки.
- `backend/data/` — исходные CSV.
- `frontend/src/` — интерфейс отчёта.

Отчёт уже читает PostgreSQL через `PrismaReportRepository`.
Файлы читает только модуль `imports`.

Прямой импорт `.xlsx` и `.xls`, загрузка файлов через HTTP и поиск произвольных
Excel-файлов сейчас не реализованы. Не описывай их как существующие возможности.

## Правила разработки

- Перед изменениями изучи соответствующий код, тесты и документацию.
- Сохраняй незавершённые изменения пользователя. Не откатывай посторонние правки.
- Соблюдай существующий стиль и настройки TypeScript.
- Используй понятные имена, небольшие функции и явные зависимости.
- Следуй SOLID, KISS и YAGNI соразмерно размеру проекта.
- Не вводи дополнительные слои, базовые классы или зависимости без задачи.
- Не ослабляй строгую типизацию для устранения ошибок компиляции.
- На внешних границах проверяй данные во время выполнения:
  TypeScript-типы не заменяют валидацию.
- Обрабатывай ошибки как `unknown`; не скрывай сбои пустым `catch`.
- Для файлового и сетевого ввода используй асинхронные операции.
  Не добавляй блокирующий ввод в обработчики HTTP.
- В комментариях объясняй причины и ограничения, требующие пояснения.

## NestJS и границы ответственности

- Организуй код по функциональным модулям.
- Контроллеры принимают запросы и делегируют выполнение сервисам.
- Сервисы организуют сценарии использования.
- Репозитории выполняют операции с хранилищем.
- Парсеры преобразуют внешний формат во внутренние модели.
- Получай зависимости через конструктор и контейнер NestJS.
- Экспортируй из модуля только необходимые другим модулям провайдеры.
- Сохраняй контракты `ReportRepository` и `ImportRepository`.
- `calculateReport` должен оставаться чистой функцией:
  без NestJS, Prisma, файлового ввода и зависимости от текущего времени.
- Общие правила учёта размещай в доменных функциях и валидаторах.
  Не дублируй их в контроллере, импортере и интерфейсе.

## Деньги, даты и расчёт

- В расчётах используй целые копейки `bigint`, в PostgreSQL — `BIGINT`.
- Не преобразовывай денежные значения в JavaScript `number`.
- На входе проверяй точность до копейки и диапазон PostgreSQL `BIGINT`.
- В API возвращай суммы строками с двумя знаками после точки.
- Календарные даты передавай как `YYYY-MM-DD`, храни как PostgreSQL `DATE`.
- Преобразование дат не должно зависеть от локального часового пояса процесса.
- Сохраняй детерминированное распределение копеек.
- Не удаляй отменённые работы и возвращённые платежи из исходной истории.
- Изменение учётного правила сопровождай обновлением тестов и `DECISIONS.md`.
- Не исправляй спорное бизнес-правило молча только потому, что другой вариант
  кажется привычнее. Покажи его влияние и зафиксируй принятое допущение.

Особое внимание: сейчас возвращённый платёж учитывается в день возврата
и исключается со следующего дня. Это неподтверждённое допущение,
закреплённое существующим тестом.

## Импорт и PostgreSQL

- Текущий импорт читает комплект `contracts.csv`, `works.csv`, `payments.csv`
  из `DATA_DIR`.
- До записи проверяй весь комплект: формат, поля, статусы, даты,
  повторяющиеся ID и ссылки между сущностями.
- Сейчас ссылки должны разрешаться внутри импортируемого комплекта.
  Поддержку отдельных дельт вводи как отдельное изменение поведения.
- Повторная загрузка одних записей не должна создавать дубликаты.
- Используй постоянные исходные ID и ограничения уникальности в PostgreSQL.
  Имя подрядчика, сумма и назначение платежа не являются надёжными ключами.
- Сохраняй атомарность импорта: все учётные данные и отметка успешного импорта
  записываются в одной транзакции.
- Сохраняй блокировку, сериализующую конкурирующие импорты.
- Отсутствие строки в новом файле не означает удаление из базы.
- Не добавляй каскадное удаление учётных данных.
- Чтение набора данных для отчёта должно получать согласованный снимок.
  Сейчас используется транзакция `RepeatableRead`.
- Меняй схему миграциями. Сохраняй SQL-ограничения, включая `CHECK`
  и составной внешний ключ платежа на работу того же договора.
- Не редактируй уже применённые миграции; добавляй новые.
- Не редактируй генерируемый клиент `backend/src/generated/prisma/`.
- Используй параметризованные запросы. Для SQL, необходимого для блокировок,
  диагностики или миграций, сохраняй безопасную передачу значений.

Первоначальная загрузка, расписание и ручной запуск используют общий сценарий импорта.
По умолчанию обновление выполняется в начале каждого часа по `Europe/Moscow`.
После успешной первоначальной загрузки перезапуск не перечитывает CSV.

Текущие ограничения:
- Нет проверки версии или даты исходной выгрузки: старый файл может
  перезаписать новые значения.
- Нет полной истории импортов и изменений сущностей.
- `import_states` хранит только время последнего успешного импорта.
- Три файла читаются отдельно; единую версию комплекта обеспечивает поставщик файлов.

Не представляй эти ограничения как уже решённые.
При добавлении Excel используй существующую внутреннюю модель и валидацию.
Сначала определи устойчивые ID, состав комплекта и порядок разрешения конфликтов.

## API и интерфейс

- Сохраняй публичный контракт `GET /api/report?date=YYYY-MM-DD`.
- Проверяй HTTP-вход через DTO и общий `ValidationPipe`.
- Документируй изменения API через Swagger вместе с кодом.
- Для ошибок используй подходящие HTTP-статусы и понятные сообщения.
- Не раскрывай пароли, строки подключения и внутренние сведения в ответах.
- Интерфейс отображает рассчитанные backend суммы и не повторяет учётную логику.
- При обновлении данных показывай состояние запроса и его результат.

- Настройки получай через конфигурационный слой.
- Проверяй обязательные значения при запуске.
- Не сохраняй секреты в Git или логах.
- Обновляй `.env.example` и README при изменении настроек и запуска.

## Проверки

Используй существующие команды из `package.json`; менеджер пакетов — npm.

Для изменений backend из `backend/`:
- `npm test`
- `npm run build`

Для изменений Prisma:
- `npm run prisma:validate`
- Проверка новой миграции на отдельной тестовой базе.

Для изменений frontend из `frontend/`:
- `npm run build`

Для изменений Compose из корня:
- `docker compose config --quiet`
- `docker compose -f docker-compose.dev.yml config --quiet`

Интеграционным тестам нужен `TEST_DATABASE_URL`.
Они создают и удаляют собственные временные схемы.
Используй отдельную тестовую базу.
Без этой переменной проверки PostgreSQL и HTTP пропускаются:
такой запуск не подтверждает работу интеграции с БД.

Добавляй содержательные тесты при изменении расчёта, импорта и ограничений данных.
Для изменений только Markdown достаточно сверки с кодом и проверки документации.

В отчёте о работе указывай, что изменено, какие проверки выполнены,
что пропущено и какие существенные ограничения остались.
